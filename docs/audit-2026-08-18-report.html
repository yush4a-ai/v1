Фундамент устойчив, но три зоны требуют внимания до масштабирования

Ядро системы — хранилище, авторизация, изоляция каналов — уже прошло два полных цикла аудита и точечные проверки сегодня: 20+ находок закрыто, включая три с уровнем security (login CSRF, анонимный доступ к боевому токену, утечка секрета в тестах). Архитектура выдерживает рост числа каналов линейно, без квадратичных циклов, и падение одного канала не задевает остальные.

Но три области ещё не получили такого же внимания: Clip Engine не сохраняет результат создания клипа вообще (только лог), Executor допускает повторное исполнение задания через race condition в reclaim-логике, а треть MEDIUM-находок из прошлого цикла остаётся открытой. Ни одна из них не блокирует текущую работу — но каждая создаст более дорогой инцидент по мере роста нагрузки.

06Executor / Pipelines

● RISK

Потеря аудита при исключении в батче — закрыто. Реальный race condition в reclaim-логике — не закрыт, потенциально приводит к двойному исполнению банов/таймаутов.

FIXEDПотеря аудита при исключении посреди батча — roadmap #10

_run_per_target теперь оборачивает каждый вызов в try/except, сбой одной цели не прерывает обработку остальных и не стирает уже накопленные succeeded/failed.

NOT FIXEDreclaim_stuck_actions не проверяет, жив ли исполнитель — race condition

Условие реклейма — только started_at < cutoff, без heartbeat/lease/owner-токена. Точная цепочка: executor A берёт задание на 40 целей, обработка растягивается >120с (цепочка временных 5xx — не редкость), reclaim_stuck_actions возвращает задание в pending, не проверяя, что A всё ещё активно его исполняет. Executor B берёт то же задание, оба параллельно бьют Helix по одному списку user_id.

Для TIMEOUT это не no-op: повторный вызов обновляет длительность таймаута, а prior_timeouts инкрементируется дважды за одно логическое действие — раздувает будущую эскалацию сильнее, чем должно быть. Комментарий в коде осознаёт проблему (twitch_api.py:236-241), но исправлен только триггер (Ratelimit-Reset на 5xx), не сама гонка.

UNVERIFIED ASSUMPTION«Helix идемпотентен» — допущение в докстринге, не проверено тестом

Docstring reclaim_stuck_actions утверждает: «ban_user()/timeout_user() в Twitch Helix идемпотентны». В кодовой базе нет теста, который бы проверял это против мокового сценария повторного вызова. Для BAN это правдоподобно (конечное состояние одно), для TIMEOUT — неверно (см. выше).

Очереди — поведение при переполнении

asyncio.Queue (чат, maxsize=10000): при переполнении событие теряется безвозвратно, задокументировано намеренно — чтение чата не должно ждать. Счётчик дропов не троттлится, лог — не чаще раза в минуту.

SQL-очередь заданий: никогда не отбрасывает, растёт без ограничения при заторе. FIFO строго по id, starvation между каналами структурно невозможен (разные файлы БД), starvation внутри канала теоретически возможен при устойчивом заторе — не приоритизируется.

Единственная таблица со словом «clip» — mod_clip_token, и это исключительно credential-хранилище OAuth-токена, не история созданных клипов. Если Twitch создал клип (физически существует), но процесс упал до записи лога — бот навсегда не знает об этом клипе. Панель не может показать историю клипов, потому что данных нет ни в памяти между рестартами, ни на диске.

NOT DONEРиск дублирования клипа через сам Helix-retry

create_clip использует общий _request с ретраями на TransportError/5xx, без idempotency-key. Если физический POST дошёл до Twitch и создал клип, а ответ потерялся (обрыв/5xx после фактического успеха на стороне Twitch) — retry-цикл шлёт второй POST /clips, создавая второй, отдельный клип. Одно логическое событие может, в худшем случае, привести к 1-3 физически созданным клипам.

Блокировка при зависании create_clip: проверено — блокирует только собственную очередь/канал (следующие триггеры копятся в очереди этого канала до QUEUE_MAXSIZE), не блокирует event loop процесса, не блокирует другие каналы автоклипа, не блокирует модерацию чата (у той полностью отдельный HelixClient).

registry_api.py — найдена parameter confusion

STRUCTURALchannels/{broadcaster_id}/start|stop|reset_crash — broadcaster_id из пути, роль session-wide

Действие явно относится к конкретному каналу, но проверяется session-wide роль ADMIN, не role_for_profile(request, broadcaster_id). registry_api.py:173-174, 191-192, 212-213

Почему не эксплуатируема сейчас: единственные роли, проходящие _require_role, это ADMIN/OWNER, а ADMIN в этой системе уже задуман как глобальный ручной оверрайд (не per-channel сущность) — см. auth.py:702-705. Путаницы ролей по факту нет. Но код структурно не по-канальный, в отличие от остального moderation_api.py — если в будущем появится роль «ADMIN только своего канала», это станет дырой немедленно.

2. Что осталось пройти
~25 пунктов MEDIUM-списка цикла 2 не тронуты. Dead Code Hunt не исчерпывающий (15 из ~90 эндпоинтов сверено с JS). Multi-Channel не проверялся на реальном N > десятка — только статически.
3. Что нужно исправить перед добавлением новых функций
Clip Engine персистентность — если новые функции будут строиться поверх истории клипов (например, аналитика, повторные попытки), а данных нет вообще, каждая такая функция унаследует эту дыру. Race condition в executor — если добавляется больше типов массовых действий, вероятность попасть в 120-секундное окно растёт пропорционально.
4. Что можно оставить на потом
Разбиение ModerationStore на репозитории — работает корректно, боль чисто в поддерживаемости, не в надёжности. Discord 429-обработка — изолирована от ядра, максимум теряет один алерт. Соединения панели без пула — терпимо при текущем масштабе панели (один оператор, не сотни одновременных запросов).
5. Какие архитектурные изменения желательно сделать сейчас
Добавить таблицу mod_clips (или аналог) в схему ModerationStore/отдельного clip-store — до того, как автоклип станет более активно используемой фичей и объём непрослеживаемых клипов вырастет. Добавить lease-механизм в mod_action_queue (owner_pid + heartbeat) — сейчас как раз тот момент, пока схема ещё не оброс потребителями, которые будут ломаться при её изменении.
6. Какие изменения делать НЕ нужно
Не стоит сейчас трогать 13 singleton-паттернов в ModerationStore ради архитектурной чистоты — работает, риска нет, это чистый техдолг. Не стоит добавлять connection pooling в панель до реальных признаков нагрузки — преждевременная оптимизация непроверенной гипотезы. Не стоит менять ролевую модель registry_api.py (start/stop/reset_crash) — риск не эксплуатируем при текущей семантике ADMIN как глобальной роли, трогать её ради консистентности сейчас создаст больше риска, чем оставить.
