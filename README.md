# Cloudweb

Монорепозиторий Twitch-бота: ИИ-компаньон чата и анти-спам модерация в
одном процессе, плюс веб-панель управления ими. Всего процессов два —
бот и панель.

```
src/
  bot/            чат-бот: Twitch IRC, ответы через DeepSeek, голосовой ввод
  cigilbot/       движок модерации, по слоям:
    domain/         чистая логика — типы, детекторы, кластеризация, скоринг, policy
    storage/        SQLite — три независимые пары store+migrations
    integrations/   Twitch Helix, Discord, subprocess-контроль бота
    orchestration/  engine/pipeline/executor — собирают слои вместе
    detectors/      детекторы спама/ботов, вертикальный срез
    content/        словарный детектор запрещённого контента, вертикальный срез
  panel/          веб-панель (порт 8766), два экрана и общий вход
  paths.py        где что лежит — единственный источник путей, вне всех трёх пакетов
config/         пороги и веса детекторов, профили каналов
prompts/        сохранённые промты бота
scripts/        разовые утилиты: импорт реестра, replay, отчёты
tests/          615 тестов
docs/           планы, архитектура, описания частей
main.py         точка входа: чат + модерация (импортируется из run.py)
run.py          единственная команда запуска: чат-бот, модерация, панель, голос
voice_main.py   точка входа: голосовой ввод (дочерний процесс)
var/            рабочее состояние: БД, логи, pid (вне git)
```

`var/` отделён от исходников намеренно и это не вкусовщина: когда БД лежали
рядом с кодом, путь «корень проекта» незаметно означал сразу и место кода, и
место конфига, и место БД — разъехалось это только при переезде панели и
стоило бага, в котором панель писала бы токен модератора не туда, откуда его
читают.

Каталогов было три (`apps/twitch-bots`, `apps/cigilbot`, `apps/panel`), и
граница между ними порождала код: вставки в `sys.path`, отдельный модуль-
бутстрап, три `paths.py` с продублированными константами и тест, стерегущий
их совпадение, три `pyproject.toml` с `mypy_path` через `../`. Приложение
одно — всё это исчезло вместе с границей.

Пакеты (`bot/`, `cigilbot/`, `panel/`) позже переехали под `src/`, а внутри
`cigilbot/` появились слои — не возврат к трём каталогам: один `pip install
-e .`, один `.venv`, один `pyproject.toml`, `paths.py` по-прежнему вне всех
пакетов. Импорт остаётся ровно тем же (`import cigilbot`), меняется только
то, что лежит физически на диске.

## Как связаны части

Модерация работает внутри процесса бота — через очередь в памяти, без
файлов-посредников и без HTTP:

```
main.py                  cigilbot/pipeline.py (тот же процесс)
  читает Twitch IRC                         ModerationHub: движок на канал
  hub.submit(event)        --queue-->       разбирает в фоне, пишет verdict
  (возвращается сразу)                       в mod.<broadcaster_id>.db
```

Раньше между ними стояла граница процессов: `main.py` писал каждое
сообщение в таблицу `mod_inbox` на диске, а отдельный процесс на каждый
канал читал её в фоне. Теперь очередь в памяти, а `submit()` по-прежнему не
ждёт: чтение чата не должно оплачивать запись в SQLite и поход в Helix.

Цена этого решения названа прямо: очередь больше не переживает падение
процесса и не безгранична. Раньше при вставшей модерации сообщения копились
на диске и не терялись; теперь при переполнении они **отбрасываются** —
ждать нельзя, иначе тормоза модерации дойдут до чтения чата. Каждая потеря
считается и попадает в лог.

## Почему панель — отдельный процесс

Всё остальное свели в один, а её оставили снаружи, и по обратной причине:
панель ничего не считает и не исполняет. Она пишет `desired_state`,
паттерны и Attack Mode в те же БД, откуда их читает бот. Поэтому её можно
уронить, перезапустить или просто не открывать — модерация этого не
заметит. Так было не всегда: supervisor жил внутри панели, и её закрытие
останавливало перезапуск упавших консьюмеров.

Общими стали окружение и конфиг:

- **Один `.venv` в корне.** Бот импортирует и `bot.*`, и `cigilbot.*`, панель
  тоже — из двух раздельных окружений один процесс не собирается.
- **Один `.env` в корне.** Раньше в двух файлах лежали одни и те же
  `PANEL_TWITCH_*` ключи с разными значениями, потому что двум панелям на
  разных портах нужны были разные redirect URI.
- **Голос — отдельно.** `faster-whisper`/`numpy`/`sounddevice` вынесены в
  `requirements-voice.txt` (~600 МБ) и ставятся только при `VOICE_ENABLED=true`.

## Установка

```powershell
python -m venv .venv
.\.venv\Scripts\pip install -r requirements-dev.txt   # включает requirements.txt
.\.venv\Scripts\pip install -e . --no-deps             # bot/, cigilbot/, panel/, paths — импортируемы из src/
copy .env.example .env

# Только если нужен голосовой ввод (~600 МБ)
.\.venv\Scripts\pip install -r requirements-voice.txt
```

`pip install -e .` — не публикация пакета (`[project.dependencies]` пуст,
`requirements*.txt` остаётся единственным источником правды по
зависимостям), а единственный способ сделать `src/bot`, `src/cigilbot`,
`src/panel`, `src/paths` видимыми интерпретатору: Python добавляет в
`sys.path` каталог запускаемого скрипта (`run.py`, `main.py` — в корне
репозитория), не `src/`.

## Запуск

```powershell
.\.venv\Scripts\python run.py
```

Одна команда поднимает всё: чат-бота, модерацию всех активных каналов,
панель на http://localhost:8766 и — если `VOICE_ENABLED=true` — голосовой
ввод. Останавливается всё вместе по Ctrl+C.

Процессов при этом два, и граница между ними не случайна. Бот, модерация и
панель живут в одном event loop'е: `Bot.start()` и `uvicorn.Server.serve()`
— обычные корутины, делить их по процессам не за чем. Голос вынесен в
дочерний процесс, потому что faster-whisper и sounddevice в одном процессе
с twitchio роняли его без трассировки (конфликт нативных потоков, см.
`bot/voice_queue.py`) — но запускать его руками больше не нужно.

Если бот падает (протух токен, Twitch недоступен), панель остаётся жива:
она ровно то место, где токен и чинят. Верно и обратное — занятый порт
панели не мешает боту читать чат. Падение любой половины сразу видно в
логе, чтобы работающая наполовину система не выглядела исправной.

Для разработки панель поднимается отдельно, не трогая прогретое состояние
движка (скользящее окно, кэш пользователей, кластеры):

```powershell
.\.venv\Scripts\python -m panel.server   # только панель
.\.venv\Scripts\python run.py --bot-only # только бот и модерация
```

## Состояние

Модерация работает в **SHADOW-режиме**: анализирует чат и пишет вердикты в
БД, но сама никого не банит и не таймаутит, пока владелец канала явно не
включит исполнение. Phase 1 закрыт и проверен на живых каналах
(`dobriy_yura`, `paverpapa`). Следующее по плану — Phase 2, Alerts.
